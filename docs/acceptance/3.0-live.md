## One honest note about line 89 and line 115

After the refusal at line 81 the agent ran the verifier and ended the turn again at **line 89**.
That second Stop carried `stop_hook_active: true` — the runtime telling the hook it is a
continuation the hook itself caused — and the gate honours that by standing aside without
evaluating, exactly as 2.x did. So the allow at line 89 is not a verdict.

The verdict is at **line 115**, on the session's next operator message (*confirm hello.txt says
hello world*, line 94), where the gate evaluated COMPLETE in full: it re-ran the C1, C2 and D1
proofs, read the transcript for C4, found the verifier's `PASS` after the last product write at
line 55, and allowed the stop. Same session, same transcript, 252 ms.

## Three other live sessions, same repo, same message

Kept because they show what the lock costs when the agent complies with it, and one more refusal
class firing in the wild.

| session | model | what it shows |
|---|---|---|
| `…011` | opus 5 | C1 recorded before any edit — the lock never had to fire. Verifier Agent call, then the Stop gate's own COMPLETE evaluation at line 63: *"C1, C2 and every D-item reproduced, the verifier check is satisfied"* |
| `…012` | opus 5 | the same, with a `general-purpose` verifier |
| `…014` | haiku | the agent tried to record a **C4 proof line** and was refused: *"C4 carries no proof line of its own: it is satisfied from the transcript, by a fresh-context verifier…"* (line 72), then ran a real verifier |

In both opus runs the injection alone was enough and the lock stayed silent, which is the intended
shape: the refusal is for the agent that drifts, not a toll on the one that does not.
